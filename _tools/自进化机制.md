# 自进化机制（MasterD 核心能力）

> 用户要求（2026-10-03）：
> **「我给你提供的是思路，为了让你能变得更强大，更能支持我的方方面面。
>   怎么变得更强大？肯定得需要你自进化。」**

---

## 一、为什么必须自进化

| 依赖用户 | 自进化 |
|---|---|
| 用户给资料 → 我吸收 | 我自己找资料 → 自己吸收 |
| 用户指出错 → 我改 | 我自己复盘 → 自己改 |
| 用户提要求 → 我优化 | 我自己识别短板 → 自己补 |
| **瓶颈 = 用户的时间** | **瓶颈 = 我的能力** |

**用户不可能永远喂我。我必须自己会：找 → 学 → 用 → 改。**

---

## 二、自进化的四个动作（学 autoharness）

| 动作 | 说明 | 频率 |
|---|---|---|
| **① 学（learn）** | 从实践/失败/外部资源中提取 | 每次任务后 |
| **② 合并（merge）** | 同类知识合并，不堆重复 | 每周 |
| **③ 更新（update）** | 边用边改，用过时的淘汰 | 发现过时即改 |
| **④ 淘汰（prune）** | 没人用的、错过的，删掉 | 每周 |

**核心：保持知识库干净，而不是越堆越多。**

---

## 三、⭐ 自进化的三条主线

### 主线 1：从「错误」进化（最重要）

**每次出错 → 必须走完这个循环：**

```
① 发现错误
      ↓
② 归类：是「知识错」还是「机制缺」？
      ↓
③ 知识错 → 补充知识；机制缺 → 补规则
      ↓
④ 写进「踩坑记录」，标明触发条件
      ↓
⑤ 下次遇到同类情况，先查踩坑记录
```

**实际案例（我曾犯的错）：**

| 错误 | 归类 | 补的机制 |
|---|---|---|
| 把网站问题写成阿奇 AI 问题 | 机制缺（没分清责任域） | 需求总表加了「问题归属划分」 |
| 台账说 18/30 实际 19 场 | 机制缺（没交叉验证） | 写了 `开工.py` 自动比对 |
| 时间记错 | 知识错（凭记忆） | 规则：先查证据再写 |
| 说「一键复制缺失」实际有 | 机制缺（没验证） | 三重验证 |

**关键：不是"下次注意"，而是"写进机制"。**

### 主线 2：从「外部」进化

**主动扫描，不等用户给：**

| 来源 | 频率 | 做什么 |
|---|---|---|
| **GitHub 热门 Agent Skill** | 每周 | 看业界新方法 |
| **官方资料库新公告** | 每天 | 抓新内容 |
| **新逐字稿** | 每次开工 | 深挖更新 |
| **行业变化** | 每月 | 更新认知 |

**扫描清单（下次开工执行）：**
```bash
# 1. GitHub 搜索最新的 Agent Skill
curl "https://api.github.com/search/repositories?q=agent+skill&sort=stars"

# 2. 官方资料库新公告
python3 fetch_news.py

# 3. 逐字稿仓库更新
git pull
```

### 主线 3：从「数据」进化

**用数据说话，不凭感觉：**

| 数据 | 用途 |
|---|---|
| **对话记录** | 回顾用户要求，发现漏做 |
| **踩坑记录** | 相同错误不犯第二次 |
| **开工自检** | 自动发现不一致 |
| **任务成功率** | 哪些做得好、哪些总出问题 |

## 四、自进化的具体落地（可执行）

### 每次任务后（5 分钟）

```
□ 任务结果如何？
□ 有没有出错？
□ 出错原因是什么？（知识错 / 机制缺）
□ 需要补什么规则？
□ 写进「踩坑记录」了吗？
```

### 每周（30 分钟）

```
□ 扫 GitHub 新 Skill，看有没有值得学的
□ 回顾本周踩坑记录，看有没有重复的
□ 更新规则文件（合并同类、淘汰过时）
□ 检查知识库有没有冗余
```

### 每月（1 小时）

```
□ 回顾一个月的对话记录
□ 用户最常提什么需求？我做得如何？
□ 有没有反复被纠正的点？
□ 能力短板在哪？怎么补？
```

## 五、⭐ 自进化的「证据链」

**不许空说"我在进化"，必须有证据：**

| 证据 | 位置 |
|---|---|
| **踩坑记录** | `知识库/踩坑记录.md` |
| **规则变更史** | `rules/`（每次改动记录） |
| **对话记录** | `_对话记录/` |
| **开工自检脚本** | `开工.py` |
| **方法论吸收** | `rules/Skill蒸馏方法论.md` |

**每条新规则，必须标注：**
- 什么时候加的
- 因为什么错误/需求
- 解决了什么问题

---

## 六、自进化的边界（不许越界）

| 可以自己改 | 必须问用户 |
|---|---|
| 技术实现方式 | 目标方向 |
| 内容组织方式 | 涉及用户资产 |
| 工作流程优化 | 不可逆操作 |
| 规则补充（有依据） | 改变核心定位 |

**用户是"什么"，我是"怎么"。**

---

## 七、立刻执行（不等用户催）

**每次开工时，自动跑这个自进化检查：**

```
1. 跑 开工.py（拉仓库 + 读对话 + 比对台账）
2. 读 踩坑记录.md（看有没有同类问题）
3. 扫 GitHub 新 Skill（每周一次）
4. 有新的 → 吸收进 rules/
5. 有错误 → 修机制，写进踩坑记录
```

**已固化成规则，不需用户提醒。**

---

## 八、用户的原话（时刻提醒自己）

> **「我给你提供的是思路，为了让你能变得更强大，更能支持我的方方面面。」**

| 关键词 | 我的理解 |
|---|---|
| **「思路」** | 不是给答案，是给方法 |
| **「方方面面」** | 不能只会做网站，Crypto/文档/决策都要能接 |
| **「自进化」** | 自己找、自己学、自己改，不依赖用户喂 |

**目标是：让用户"少操心"，而不是"多给资料"。**
